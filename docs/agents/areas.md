# Coordinator area notes

Detailed rules and lessons for each part of the project, kept out of AGENTS.md so that file stays short. Read the section of the area you change before you change it; AGENTS.md applies to every task. Keep this file current like AGENTS.md: a change that alters a rule here updates it in the same PR.

## Solution views

- Files: `.solution.json` (manifest, with an `emoji` per repository and at the top level for this repository), `docs/solution-order.md` (owner's order), `docs/SOLUTION-DASHBOARD.md` (generated by `tools/solution.mjs`, copied from the template).
- Refresh: `npm run solution:refresh` reads every component's `main` from GitHub at one resolved commit each (set `GH_TOKEN` in the environment if the API rate limit is reached; never commit it). Commit the dashboard and the order together; the PR names the snapshot time.
- Closed order items (B-001, B-058): an order item that closed in its repository (archive, or closed in its work-item data) shows ✅ Done and is no problem. The refresh drops such items with `node tools/solution.mjs dashboard --write --prune-order` (`npm run solution:dashboard`) and renumbers the order; the refresh PR carries the order with the dashboard, and its diff of `docs/solution-order.md` is the record of what was dropped (the dashboard written in that run still lists the items as ✅ Done). An ID found nowhere still fails the refresh.
- Order format: the template's since F-004-T02 (`.solution.json` `order`; `N. repo:ID — note`, this repository `coordinator:`).
- Check: CI runs `node tools/solution.mjs check --offline` and fails only on its `order:` problems (component checkouts are absent there, and component availability is not a CI gate); `npm run check:solution` validates the manifest, the order references, sources and links through GitHub.
- Cross-repository prerequisites: a step here that waits on a component step names it in `dependsOn` as `repo:STEP-ID` (F-006-T01, F-007-T01); prose such as "(waits on grover:F-008)" is not read. List it in the step's own `externalMet` once its outcome there is checked; until then the step waits.
- Dashboard layout (template 10.21.0, F-099; adopted in F-004-T05): Summary, Solution order (emoji, link, agent and owner hours, open prerequisites), Blocked, Nothing to do, Waiting for the owner, Agent runway, Audits, reviews and harness, Gap review, open steps per project, Remaining effort, Integration outcomes, Component work, problems. A layout gap is proposed to the template (`docs/proposals/solution-order-in-template.md`), never patched into the copied tool.
- Retired (F-004-T05, 2026-11-25): the project's own overview (`tools/solution-overview*.mjs`, `docs/SOLUTION-OVERVIEW.md`, `check:order`, `solution:overview`, its fixtures). Compared on the same commits before removal; the differences the template keeps on purpose are in F-004's closure evidence.
- Refresh workflow: `tools/refresh-branch.mjs` prepares `chore/refresh-solution-views` (merge main, take main's copy of a conflicting dashboard or order, fail on any other conflict; start from main when no refresh PR is open). It runs main's copy of the tools only. It pushes and opens the PR with the repository secret `REFRESH_TOKEN` (owner decision 2026-11-24, option B), so the normal pull_request CI starts by itself; the workflow token is read-only and a missing secret fails the run. The refresh PR merges itself (owner decision 2026-11-25, F-010): the workflow enables auto-merge with branch deletion only when `tools/refresh-guard.mjs` finds nothing but the generated dashboard changed and, in `docs/solution-order.md`, only items the dashboard shows Closed dropped; otherwise it comments why and a person lands it. Auto-merge relies on main's branch protection requiring the CI check `check`; without a required check it would merge at once. The workflow uses only main's tools.
- Gap review: the dashboard's "Gap review" section; procedure in [gap review](gap-review.md), kinds in [solution gaps](solution-gaps.md). A false positive goes to the template as a proposal, not into the generated page.
- Hours: each backlog's total line, else its open records' Remaining cells; Unknown otherwise, and the solution total then reads "at least". Runway: agent steps whose prerequisites are done or doable, across repositories; cycles and unknown prerequisites are blocks, never loops.

## Cross-repository backlog

- Files: `docs/BACKLOG.md`, `docs/SOLUTION.md`.
- A record here owns a contract, a compatibility decision, an end-to-end acceptance or a coordination step. Its `Components` row links the component records it depends on; their implementation, next actions and closure stay in their own backlogs.
- A component record closes on its own criteria; never hold it open for integration here.
